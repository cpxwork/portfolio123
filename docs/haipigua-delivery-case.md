# 嗨皮瓜：修改建议与预约任务的边界

本文根据现有 `plan` 流程、接口约定与固定对话记录整理，展示需求如何进入实现和验收。不是独立的线上用户实验。

## 用户任务

已有陶笛学习兴趣和预约任务。用户说：

> 只改陶笛学习建议，每次 10 分钟，不预约时间。

用户需要新的学习建议，并没有授权变更日历。若将“10 分钟”直接解释成预约，会产生错误任务；若只保存便条，用户又没有得到所需建议。

## 首版范围与产品决策

| 项目 | 约定 |
|---|---|
| 成功结果 | 更新指定兴趣的建议，展示本轮建议，并说明没有新增预约 |
| 意图 | 使用独立的 `plan`，与 `schedule`、`feedback`、`review` 区分 |
| 模型职责 | 理解本轮意图，生成对应兴趣的学习或创意建议 |
| 确定性校验 | 兴趣引用、结构、日期与任务操作权限、失败时的状态一致性 |
| 本轮约束 | 时长、精力、程度、目标只约束本次建议，不自动写成长期偏好 |
| 历史记录 | 每条消息保留独立的建议快照，后续修改不覆盖旧消息 |
| 异常处理 | 目标不明时先确认；模型、格式或校验失败时保留原话，整轮不写入 |

## 前后端对齐

请求沿用 `POST /api/agent`：前端提供原话、本地日历基准、已有兴趣与任务、近期反馈和用户确认的事实。服务端校验输入、上下文白名单和预算。

响应中的 `analysis.intents` 表达 `plan`，`content.plans` 或 `content.explorations` 承载实际模型建议，`trace` 保留真实执行记录。前端核验后更新相应兴趣的 `aiPlan` 或 `exploration`，保存 `note.advice` 快照。

`plan` 不允许携带用于创建或改期任务的 `taskId/date/start/end/replaceTaskId`。服务端不直接写浏览器状态，客户端校验后统一应用；失败不允许出现一半成功的状态。

## 验收清单

| 输入或状态 | 预期行为 | 检查对象 |
|---|---|---|
| 已有兴趣，只修改建议 | 实际生成并更新建议，不追问预约日期 | 意图、对应角色调用、建议正文 |
| 已有任务与长期偏好 | 任务、偏好和待改期问题保持不变 | 操作前后状态差异 |
| 同一兴趣连续修改两次 | 两条消息展示各自建议快照 | 消息内容和兴趣当前建议 |
| 同时提到确定的实验时段 | 建议与忙碌事实分别处理，不移动旧任务 | 分流、忙碌记录与冲突澄清 |
| 实验时间只是一个假设 | 不把未确定的时段写入日历 | 忙碌记录与旧预约 |
| 模型或格式校验失败 | 不部分写入，保留原话以便继续 | 错误状态、草稿及业务状态 |

## 结果如何判断

验收分别检查意图、实际角色调用、输出内容和最终状态。建议生成与任务预约是不同的成功事件，不能把“回复了一段文字”直接计为“完成了行动安排”。

现有固定对话记录保留了修复前的错误和修复后的结果；软件回归、有限模型调用与真实用户使用效果分别报告。公开腾讯云站点提供规则交互演示，本机文本模型闭环的接口与验证记录单独查阅。

若开展用户试用，可按以下口径采集数据；这些是指标定义，不是已取得的增长结果：

| 指标 | 口径 |
|---|---|
| 建议交付率 | 成功返回并保存合格建议的请求数 / 有效建议请求数 |
| 非预期任务变更率 | 仅请求建议却改变预约的请求数 / 仅请求建议的有效请求数 |
| 澄清完成率 | 用户补充必要信息后完成原任务的会话数 / 进入澄清的会话数 |
| 失败后恢复率 | 失败后继续原请求并成功交付的请求数 / 支持恢复的失败请求数 |
| 用户评价 | 在交付后收集“是否有用、是否理解需求”，与软件验收结果分列 |
